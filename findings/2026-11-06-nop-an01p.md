## 一、失败的路径（按尝试顺序）

### 1. HiSuite「系统修复」—— TrustList 拒绝

设备进 `FASTBOOT & RESCUE MODE` 后点「系统修复」，日志：

```
sn=1  IsRescueMode return rescue_version: rescue0.8
sn=2  fb success  oem getencryptudid,length=64.
sn=3  fb success  oem getencryptsn,length=16.
sn=4  getudid true
sn=5  GetInfoPKI=true
fn=1  RESULT: FALSE  CAUSE: The device is not in the TrustList.
```

通道是通的（UDID 读到了），但服务端判定设备不在白名单。连点三次都是同一结果。

界面表现：`系统修复暂不支持你的设备`。

### 2. 让设备回正常系统再点「系统修复」—— 按钮是灰的

「系统修复」只在 rescue 态可点。

### 3. 怀疑是 HiSuite 版本问题 → 查 HISuite-Proxy

- 仓库 `ProfessorJTJ/HISuite-Proxy`：**已归档**（`archived: true`，最后 push 2023-08-23）
- 最新 release `3.3.0`（2022-08-28），配套 `HiSuite_11.0.0.610_OVE`
- 与本机 `17.0.0.100` 跨 6 个大版本，patch 点全对不上

结论：HISuite-Proxy 不可用。

### 4. 找响应缓存 —— 磁盘上没有

扫 `%TEMP%` / `%LOCALAPPDATA%\HiSuite` / `Documents\HiSuite`，没有落盘的响应 XML。HiSuite 是内存解析（日志里 `reader parse format ok.`）。

### 5. Wireshark 思路 —— 只能看域名

TLS + 内嵌 CA，pcap 里只有 SNI 和字节数，没有 URL。

## 二、成功的路径

### 步骤 1：定位网络层

扫 `C:\Program Files (x86)\HiSuite` 下所有 DLL/EXE：

```
httpcomponent.dll  201,968  bytes
  hicloud                  × 2
  -----BEGIN CERTIFICATE-- × 51   ← 内嵌 CA
  SSL_CTX_set_verify       × 1
  libssl                   × 1
```

→ 网络层是 `httpcomponent.dll` + OpenSSL 3（`libssl-3.dll` / `libcrypto-3.dll`）。

### 步骤 2：Frida 挂进程

```powershell
Stop-Process -Name HiSuite -Force
frida -f "C:\Program Files (x86)\HiSuite\HiSuite.exe" -l tools/hook_ssl.js -o capture_out.log
```

首个输出确认 hook 成功：

```
==== HOOKED: SSL_write,SSL_write_ex,SSL_read,SSL_read_ex,SSL_CTX_set_verify ====
[set_verify mode=1]
```

### 步骤 3：走对通道

**关键**：设备必须在**正常系统**（不是 fastboot），然后点「系统更新」→「检查更新」。

此时日志里**没有** `IsRescueMode`，也**没有** `fb` 命令，直接进查询：

```
sn=26  localFullBase is:G6.0 localFullCust is:G6.0 localFullPreload is:G6.0
sn=29  full_back have new version.
sn=30  Enter BL SystemFull.
sn=33  devD[s_xxx_n],devM[NOP-AN01P],req[<REDACTED>]
sn=34  reader parse format ok.
fn=5   RESULT: FALSE  CAUSE: invalid.        ← 因为已是同版本，HiSuite 中止刷写
```

**注意**：虽然 HiSuite 最终以 `invalid` 中止（目标版本=当前版本，无需更新），但**在此之前它已经把查询和清单请求全发出去了**——这正是我们要抓的东西。

## 四、关键发现：同版本号、不同构建

```
OTA 包内内核：  Linux version 5.10.43 (HarmonyOS@localhost) (clang 12.0.7, r416183b1)
                #1 SMP PREEMPT Fri Apr 26 13:47:07 CST 2024

设备实跑内核：  同版本号 5.10.43、同 clang、同构建机
                #1 SMP PREEMPT Thu Aug 20 18:03:37 CST 2026
```

两者相差两年四个月，但**版本号、编译器、构建主机完全相同**。

对照另一个样本（HarmonyOS 3.0 的 OCE 机型）：

| | OCE 2022 | NOP 2024 | NOP 2026（设备实跑） |
|---|---|---|---|
| Image 大小 | 69,517,996 | 73,521,236 | — |
| `0x1000` 处前 8 条指令 | `sub sp,sp,#0x90` … | **完全相同** | — |
| 代码密度 | 99.6% | 99.6% | — |

`_text` 开头的机器码逐字节一致，说明是同一套 head.S / 编译配置。

**推论**：拿 OTA 包内的内核做符号表/结构偏移研究时，必须先用 banner 对齐构建期——同版本号不代表同二进制。
